# DrasiWake Raft 高可用设计规格

- 日期：2026-10-07
- 状态：设计已获用户确认；待规格文档审阅
- 参考实现：`E:\GitHub\Slik\src\SlikCache`
- 目标平台：.NET 10；DotNext.AspNetCore.Cluster（与参考项目使用的 6.9.0 对齐）

## 1. 背景与目标

DrasiWake 当前以一个活动 Host 和一个 SonnetDB 目录运行。Host 通过独占文件锁阻止多个进程同时操作同一目录；该锁保护单机数据完整性，但不提供多副本故障切换。

本设计在保留现有 `IBridgeStore`、SonnetDB 及 outbox 投递语义的基础上，引入 DotNext Raft 集群。目标集群为三个投票节点，可容忍一个节点故障。每节点持有自己的本地数据库和 Raft 日志；Raft 已提交的业务命令是集群状态的权威来源，SonnetDB 是该节点的持久化物化副本。

设计决策：

- 集群必须保留多数派才能提交状态变更或执行受 Raft 写入保护的业务工作。
- 任一时刻仅当前 leader 运行 Drasi 接收、快照对账和 outbox 分发。
- 允许 leader 在 Gateway 已受理后、受理结果尚未复制提交时故障；新 leader 可重放相同的 outbox 请求，并依靠现有稳定幂等键和 Gateway 幂等保留策略去重。
- 成员支持运行时 Add/Remove，通过 TLS 上的内部 gRPC 管理端点及独立 Bearer Token 保护。
- 保留单节点运行形态，供本地开发和既有部署使用；该形态也使用同一 Raft 状态机路径。

## 2. 范围

### 包含

- Host 中的 DotNext Raft 集群引导、状态机和 leader 生命周期协调。
- 所有影响业务持久状态的写操作经 Raft 多数派提交后应用到每节点本地 SonnetDB。
- 可用于恢复节点本地投影的完整 Raft 状态快照。
- 新 leader 的恢复、Drasi 全量对账及 outbox 恢复顺序。
- 内部 TLS 传输、成员管理 gRPC、独立管理令牌配置和成员变更校验。
- 单节点兼容、节点配置验证、运维文档、遥测和多节点测试。

### 不包含

- 共享 SonnetDB 目录、共享文件系统数据库或另一种分布式数据库后端。
- exactly-once 外部副作用、对 Drasi 中间变化的逐项事件保留保证。
- 自动弹性扩缩容、跨地域灾备、跨版本滚动升级协议或自动 RTO 保证。
- NativeAOT 发布。

## 3. 架构与职责边界

### 3.1 集群节点

每个节点至少配置唯一 NodeId、Raft 监听地址、独立 Raft 数据目录、独立 SonnetDB 目录和引导成员地址。不同节点不得共享 SonnetDB 目录，也不得复用 NodeId 或 Raft 数据目录。现有目录所有权锁仍保留，用于阻止同一节点数据库被两个进程同时打开。

Host 注册 DotNext 的 Raft HTTP/2 协议处理器、持久化集群配置、持久化状态机，并通过 `JoinCluster` 加入。实现以 SlikCache 的 `UseConsensusProtocolHandler`、`UsePersistentConfigurationStorage`、`UseStateMachine<T>`、`JoinCluster` 及 leader router 模式为参考；实际 API 和行为须在实现阶段按选定 DotNext 版本验证。

Raft/WAL/snapshot 路径与 SonnetDB 路径分别配置。复制载荷包含现有 outbox 中的业务输入数据，因此两类存储都按敏感业务数据保护。集群节点间通信使用 TLS。

### 3.2 Raft 状态机与本地 SonnetDB

在持久化适配层引入实现 `IBridgeStore` 的 Raft 适配器，并将现有 SonnetDB store 保留为每节点投影读写器。适配器将写请求转换为有版本、确定性、可重放的命令；leader 通过 Raft 复制命令，节点状态机按相同提交顺序应用命令到本地 SonnetDB。

命令包含其结果所需的时间戳、标识符和状态转换值，不能在每个副本应用时各自生成当前时间或随机标识。命令对重复应用必须安全，且要区分“客户端重试同一命令”和“之后发生的新业务操作”。

应覆盖所有可能影响后续行为的可变持久状态，至少包括：

- Wake outbox 记录及其状态变更。
- Snapshot checkpoint。
- 会话和规范身份的 key mapping。
- 启动期间对现存活动 outbox 记录执行的 target 补全或校验性修复。

配置注册表、Drasi/Gateway 连接配置、令牌和证书不复制进业务 Raft 命令。`MarkAcceptedWithCheckpointAsync` 必须作为单一状态机命令应用，确保受理状态与 checkpoint 不会分裂。

`LoadDispatchableAsync` 同时读取候选项并改变其状态。实现应先在 leader 的本地投影上读取候选项，再把精确的候选 ID 集合作为 claim 命令提交；只有 claim 成功提交后才向 Gateway 调用。所有分发 worker 仅由 leader 运行，因此不会存在两个有效 leader 同时 claim 的正常路径；状态机仍需对过期状态、重复命令和并发重试进行防御性校验。

只读查询可以从节点本地投影提供，但任何会影响业务进度或后续恢复的状态变更均须经 Raft 提交。仅在某节点已应用到集群当前可服务索引、且业务配置与集群一致时，该节点才可参与业务工作。

### 3.3 快照和落后节点恢复

Raft snapshot 必须包含重建完整业务投影所需的状态，而不只是最后应用索引。这样在日志压缩、节点全新加入或节点长期落后时，仍可恢复 SonnetDB。

快照需要与其 Raft 应用索引绑定，写入时捕获一致的状态。恢复流程先校验并恢复快照，再顺序应用其后的已提交命令。恢复失败或投影索引落后时，该节点标记为未就绪，不得运行业务 worker，也不得作为已追平成员提供业务写服务。已存在的本地投影不得在快照校验成功之前被不可逆地清空或替换。

## 4. Leader 生命周期与请求流程

### 4.1 启动和新 leader 激活

1. 验证节点身份、监听/数据目录、TLS 和管理令牌配置；确保 SonnetDB schema migration 已应用。
2. 启动或加入 Raft 集群，恢复 Raft 状态机 snapshot 及已提交日志，确认本地 SonnetDB 投影已追平。
3. 非 leader 节点保持业务 worker 停止，只参与 Raft 复制、状态应用和受保护的成员管理。
4. 新 leader 获得领导权后，以新的 leadership epoch 启动恢复协调；先恢复中断的 outbox 状态，再枚举 Drasi 查询并读取最新快照完成对账。
5. 恢复/对账完成后才启动 Drasi 信号接收、周期性对账和 outbox 分发。
6. 丢失领导权或集群失去多数派时，取消该 epoch 的 worker 和未完成工作；任何无法提交的状态转换都不得作为成功处理。

现有 `RecoveryCoordinator` 需支持按领导权 epoch 重复初始化，而不是只在进程启动时运行一次。所有启动、对账和分发工作在新 leader 上都必须可重放。

### 4.2 Outbox 与 Gateway 故障窗口

分发顺序为：复制并提交 `Dispatching` claim、调用 Gateway、复制并提交“Accepted + checkpoint”，再查询和复制执行状态。超时或结果不确定时遵循现有 outbox 错误分类与 retry policy。

若节点在 Gateway 已接受请求、但 `Accepted + checkpoint` 尚未提交时退出，新 leader 从已提交状态恢复 outbox，并可使用同一稳定幂等键重新发送。可靠性契约是可恢复的至少一次投递，要求 Gateway 幂等键跨节点共享且保留期覆盖最长 retry age；本设计不宣称严格 exactly-once。

Raft 的多数派提交是状态变更的必要条件。没有多数派时集群不得继续处理需持久状态推进的业务工作。测试还须覆盖已经发出的外部请求与领导权丢失并发的窗口，并验证重复请求仍使用相同幂等键。

## 5. 成员管理与安全

### 5.1 启动成员与运行时成员变更

部署配置提供初始成员地址用于引导集群；启动后以 DotNext 持久化的集群配置为成员事实，不得在每次重启时用初始配置覆盖已提交的动态变更。新节点通过已知成员加入并追平状态后才可参与业务工作。

运行时 Add/Remove 通过独立内部 gRPC 管理端点完成，并由 leader 转发或执行成员变更。操作应遵循 DotNext/Raft 的成员变更安全流程；拒绝非法地址、重复或无效成员操作，并在无多数派时拒绝变更。移除成员需在成员变更提交后才能退役其本地数据。API 不提供任意 Raft 命令写入能力。

管理端点使用 TLS 和独立 Bearer Token。令牌由环境变量或部署 secret provider 配置，不写入 appsettings、Raft 配置、日志或响应体。管理操作记录安全的审计信息（操作类型、成员稳定标识、结果和发起时间），不得记录令牌。传输层需限制在内部网络；管理端点的 gRPC 服务必须对每个请求执行令牌校验。

### 5.2 节点业务配置一致性

同一集群的节点必须运行兼容版本并使用一致的有效绑定注册表、Drasi 身份、OpenClaw target 映射及影响重试/分发行为的设置。集群引导时，将这些功能性配置的规范化指纹作为集群业务元数据持久化；不包含令牌、私钥、NodeId、监听地址或本地数据路径。节点启动时必须与已提交指纹匹配，才可成为可服务 leader。

Add 成员前，当前 leader 通过 TLS 管理 gRPC 查询候选节点的应用版本和功能性配置指纹；仅当版本兼容且指纹匹配时才提交成员变更。管理 Bearer Token 在集群管理面共享并逐节点安全注入，以便执行此受保护的兼容性查询。功能性配置变更不在本阶段内热更新；须停止业务处理，通过单独的集群维护流程协调更新所有节点及已提交指纹，完成一致性检查后再恢复服务。此流程不得静默接受部分节点的配置漂移。

## 6. 配置和运维

HA 配置需显式区分节点本地和集群级项目，至少包括：

| 项目 | 要求 |
| --- | --- |
| NodeId | 集群内唯一且重启后稳定。 |
| Raft 地址 | 每节点唯一、对其他成员可达，使用 TLS。 |
| 引导成员 | 首次建群/加入使用；不能覆盖已持久化成员配置。 |
| Raft 数据目录 | 每节点独立，持久化 WAL、集群配置和 snapshots。 |
| SonnetDB 目录 | 每节点独立，禁止在副本间共享。 |
| 内部管理 gRPC | 独立监听配置、TLS 和独立 Bearer Token。 |
| 业务设置 | 各节点功能配置等价；令牌/私钥逐节点注入。 |

本地单节点开发保持原有启动路径和配置可用，通过单成员 Raft 集群使用相同状态机实现。HA 运维指南说明三节点部署、端口/证书、持久化卷、节点加入/移除、失去多数派和节点恢复处理。固定 RTO 暂不作为承诺；先通过故障测试和遥测采集选举、追平和重新对账耗时，再依据实测设定目标。

## 7. 可观测性与错误处理

复用现有 OpenTelemetry ActivitySource/Meter 和结构化日志约定，新增至少以下观测：

- 节点角色、leader 变化和当前 leadership epoch。
- 多数派/集群可写状态。
- Raft 提交索引与本地应用索引差距、snapshot 创建/恢复结果和耗时。
- follower 追平状态、成员 Add/Remove 成功或失败。
- 因失去多数派或领导权而停止的业务工作。
- 重新对账、outbox 恢复和故障切换耗时。

不记录事实载荷、Bearer Token、私钥或异常消息中的敏感内容。关键操作失败必须显式记录固定错误类别，并使节点保持未就绪/停止处理；不得以静默回退到本地独立写入的方式“继续服务”。

## 8. 验收与测试

### 单元和适配器测试

- 验证每种 Raft 命令的序列化版本、确定性字段、应用顺序、重复应用和非法状态拒绝。
- 验证 `Accepted` 与 checkpoint 在同一个命令中恢复，不能出现仅一侧已提交的状态。
- 验证 dispatch claim 只有提交后才触发 Gateway 调用，且失败时不伪造成功状态。
- 验证 snapshot 导出/校验/恢复包含完整可变业务状态，恢复后与源状态等价。
- 验证 SonnetDB 单目录所有权锁和既有单节点持久化测试仍然通过。

### 多节点集成测试

使用三个真实 DotNext 节点、独立端口和隔离的 Raft/SonnetDB 目录，验证：

1. 三节点多数派提交命令后，所有追平节点投影一致。
2. leader 故障后其余两节点选出新 leader；新 leader 完成恢复/Drasi 对账并继续处理 outbox。
3. leader 在 Gateway 已受理后、接受状态提交前故障；重放使用相同幂等键，mock Gateway 最终仅创建一个逻辑 invocation。
4. 少于多数派时不能提交新状态、不能继续分发，并且恢复多数派后能追平。
5. 节点重启后从 snapshot 和后续已提交日志重建投影；落后节点追平之前不启动业务工作。
6. 运行时添加节点、等待其追平、移除节点，以及非法/无授权成员管理请求的拒绝。
7. 单节点配置可启动并保持原有用户可见行为。

测试必须用明确的状态断言验证已提交/未提交边界、跨节点数据相等、Gateway 幂等键相同、无多数派期间 outbox 未推进；不能仅以进程仍运行或 API 可连通作为 HA 验收。

## 9. 实施阶段需验证的技术细节

- DotNext.AspNetCore.Cluster 6.9.0 的 ASP.NET Core Hosting、HTTP/2/TLS、持久化 cluster configuration、状态机 snapshot 生命周期及节点成员变更实际 API。
- 运行状态机应用失败时 DotNext 对节点健康、日志重放和 snapshot 的行为；实现必须确保本地 SonnetDB 投影可从已提交 Raft 状态重建。
- DotNext 集群对节点/命令版本兼容性的边界；第一阶段若无安全兼容协议，则要求集群成员采用相同应用版本并明确禁止混合版本变更。
- 管理 gRPC 的身份验证与传输部署方式，以及令牌轮换操作流程。
- 通过三节点故障测试测得的 failover 和追平时间；之后再制定明确的 RTO/SLO。
